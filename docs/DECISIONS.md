# Decisions

Low-impact decisions taken while building the project, with the reason. Newest last.

| # | Date | Decision | Choice | Why |
| --- | --- | --- | --- | --- |
| 1 | 2026-10-25 | Event domain (synthetic) | E-commerce events: `page_view`, `add_to_cart`, `order_placed`, `payment` | They allow joins, sessions and funnels, which exercise every streaming concept the project wants to show |
| 2 | 2026-10-25 | Iceberg catalog | Iceberg REST catalog | The simplest catalog that Spark, PyIceberg and Trino all speak; Nessie and Polaris add features the demo does not need |
| 3 | 2026-10-25 | Python consumer sink | Write Iceberg directly with PyIceberg | The consumer owns a real table commit, so "commit offsets only after the write is durable" means something; raw Parquet files would push that problem to Spark |
| 4 | 2026-10-25 | Dashboard | None for now; Trino queries in the README | Keeps the stack small; a dashboard can come later without changing the tables |
| 5 | 2026-10-25 | Local object storage (the brief says MinIO) | An S3-compatible server behind generic `S3_*` settings, the same choice as `cdc-streaming-demo` | The MinIO community repository was archived in April 2026 and `minio/minio` no longer resolves on Docker Hub (checked on 2026-10-25); every client here only speaks S3, so the server is swappable |
| 6 | 2026-10-25 | Coexistence with `cdc-streaming-demo` | Compose project `kafka-streaming-lakehouse`, no `container_name`, every host port in `.env`, bound to 127.0.0.1, defaults in the 1xxxx range | The sibling runs Kafka and S3 storage on the usual ports (9092, 9000, 8090, ...); both stacks must run on one machine |
| 7 | 2026-10-25 | Name of the plan document | `docs/PLAN.md` (the program brief says `docs/REFACTOR_PLAN.md`) | This is a new project, not a refactor; the sibling uses the same name |
| 8 | 2026-10-25 | How phases ship | One PR per phase, each stacked on the previous branch: compose + producer, consumer + bronze, Spark silver/gold, Trino + end-to-end check, schema evolution + DLQ demo, CI | Reviewable PRs while earlier ones wait for merge |
| 9 | 2026-10-25 | Versions | Confluent Platform 8.3.2 (KRaft) for Kafka and Schema Registry, RustFS 1.0.3, Iceberg 1.12.0 with Spark 4.1.3, PyIceberg 0.12.0, Trino 484, confluent-kafka 2.16.0, Kafbat UI v1.5.0 | Current stable lines on 2026-10-25. Spark stays on 4.1 because Iceberg publishes no runtime for Spark 4.2 yet |
| 10 | 2026-10-25 | Iceberg REST catalog image | `apache/iceberg-rest-fixture` pinned by digest (the `latest` build of 2026-04-29), SQLite catalog in WAL mode on a named volume | The newest numbered tag (1.10.1) predates the WAL fix for the SQLite backend; a digest pin is as reproducible as a tag |
| 11 | 2026-10-25 | Package and CLI name | `lakestream`, one package with a Typer CLI used as the entry point of every container | Short and descriptive; one install and one entry point for producer, consumer, Spark jobs and checks |
| 12 | 2026-10-25 | Topic layout | One topic `shop.events` (6 partitions, key `user_id`) carrying a flat `ShopEvent` envelope; a DLQ topic `shop.events.dlq` | Sessions and funnels need per-user ordering across all four event types, which only one keyed topic gives; one bronze table and one atomic append per batch |
| 13 | 2026-10-25 | DLQ and retries | Poison records go to the DLQ with the original bytes and the error plus original coordinates in headers (Kafka Connect convention); transient sink errors retry the whole batch in process with bounded backoff, then the consumer exits without committing | The sink is a batch commit, not a per-record call, so a retry topic would add moving parts without a benefit |
| 14 | 2026-10-25 | Bronze idempotency | Each PyIceberg append stores the per-partition Kafka offsets it holds in the snapshot summary; on assignment the consumer resumes at max(committed offset, last written + 1) | The snapshot summary commits atomically with the data, so a crash between the Iceberg commit and the Kafka offset commit cannot write a batch twice |
| 15 | 2026-10-25 | Gold write strategy | Silver is a Structured Streaming job; gold is a Spark batch recompute from silver that replaces each gold table in one snapshot | Append-mode watermark aggregations never emit the last windows when data stops, so an `availableNow` demo would miss them; a recompute is deterministic and re-runnable, and the end-to-end check can assert exact counts |
| 16 | 2026-10-25 | Event time and watermark | Event time comes from a fixed synthetic base, never the wall clock; silver watermark 3 hours, longer than any producer run (max span 150 minutes); a separate optional "too late" scenario shows records dropped by the watermark | Exact, repeatable counts in silver and gold whatever the micro-batch split; late (out-of-order) events still land in their own event-time windows |
| 17 | 2026-10-25 | Spark checkpoints | Named volume `spark_checkpoints`, not S3 | Iceberg data goes through S3FileIO; checkpoints on S3 would need `hadoop-aws` and the AWS SDK bundle only for that |
| 18 | 2026-10-25 | Integration tests | Run against the compose stack (marker `integration`), not testcontainers | The tests exercise the real wiring of the services, and a recent testcontainers Kafka bug (`get_exposed_port`) is avoided |
| 19 | 2026-10-25 | How `make up` waits for the one-shot init jobs | Phase 1: `up --wait` only for `kafka` and `schema-registry`, then `docker compose run --rm` for `kafka-init` and `schema-init`. From phase 2 on, a plain `up --wait`, because the consumer depends on every init job with `service_completed_successfully` | Compose 2.40 `--wait` waits for "completed successfully" only when an active service depends on the one-shot with that condition; otherwise it waits for "running" and fails with `exited (0)` once the job ends (read in `pkg/compose/start.go` and `convergence.go`). Before the fix, `kafka-init` only passed because its JVM was still running at the first poll |
| 20 | 2026-10-25 | Host-side address of the stack | Kafka advertises `127.0.0.1:${KAFKA_PORT}` on its external listener, and every host-side default (Kafka, Schema Registry, S3, Iceberg REST, Trino) uses `127.0.0.1`, not `localhost` | Ports are published on 127.0.0.1 only. On Windows `localhost` resolves to `::1` first, so every new connection waited about 2 s for the IPv6 attempt to fail (measured: TCP connect 2.05 s vs 0.01 s, a bronze scan 2.13 s vs 0.08 s), which made the host-side consumer integration test time out |
| 21 | 2026-10-25 | Zombie writers on bronze | Before each append the consumer refreshes the table and reads `ingest.offsets` of its group and topic; if any partition already holds an offset at or past the batch's first offset it raises `OffsetFenceError` (never retried), logs that the batch was fenced, exits without committing and compose restarts it | A replica whose append stalls past `max.poll.interval.ms` is evicted, another replica takes its partitions and writes the same offsets, then the stalled commit lands and rows are written twice. The append asserts the parent snapshot, so a check on refreshed metadata is atomic with the commit, but only because bronze sets `commit.retry.num-retries=0`: PyIceberg would otherwise rebuild a conflicting append on the new head and retry it itself, dropping the assertion. With 0 retries a concurrent commit gives a 409 that reaches the consumer, which refreshes and checks again. Spark maintenance on bronze then fails instead of retrying if a consumer commits at the same instant, and is simply re-run. The REST client sets no HTTP timeout, so the fence (not a timeout) is what makes stale writers safe |
| 22 | 2026-10-25 | Bronze expiry clamp in `maintain` | The cutoff is the earliest commit time among the snapshots that `silver_events` and `silver_rejects` resume from, each read from `offsets/<last batch under commits/>`; no committed batch, an unknown snapshot or an unknown offset-log version means no bronze expiry | Both queries read bronze, so either one can break on an expired snapshot. The newest `offsets/N` is written before batch N runs, while a restart re-reads from the last committed batch's end offset |
| 23 | 2026-10-25 | Spark job details PLAN.md leaves open | `ops.job_runs` is unpartitioned; silver counts written rows with `observe` (sink progress has no row count for Iceberg); gold reads silver at the snapshot of its `main` ref; `make silver/gold/maintain` use `run --service-ports` so the Spark UI is reachable; the JRE comes from the `jammy` Temurin variant | A few rows per run need no partitions; observed metrics are exact per batch; one pinned snapshot keeps the three gold tables consistent; `compose run` publishes no ports otherwise; Temurin builds target an old glibc baseline, so the JRE runs on bookworm |
| 24 | 2026-10-25 | Bronze expiry and `Trigger.AvailableNow` | The bronze cutoff also keeps the snapshot of each silver query's initial offset (`sources/0/offsets/0`), so in practice bronze snapshots are not expired while the silver checkpoints exist; compaction still runs | Found on the stack: after `maintain --older-than-minutes 0` expired the first bronze snapshot, the next available-now silver run failed with "Cannot load current offset at snapshot ..., the snapshot was expired or removed". In iceberg-spark-runtime-4.1_2.13 1.12.0, `SparkMicroBatchStream.prepareForTriggerAvailableNow` calls `latestOffset(initialOffset, ReadLimit.allAvailable())` (read with `javap`), so the initial snapshot must survive. A processing-time trigger with a stop-when-idle loop would avoid it, at the cost of a less exact stop condition; resetting the silver checkpoints (a full silver rebuild) lifts the limit |
| 25 | 2026-10-25 | Trino service details PLAN.md leaves open | `lake.properties` uses `fs.s3.enabled=true` (the name in the Trino 484 docs, `object-storage/file-system-s3.html`; `fs.native-s3.enabled` is the older name) with keys and region from `${ENV:...}`; heap set with `JAVA_TOOL_OPTIONS=-Xms512m -Xmx1g`; the image's own health probe with a 90 s start period; trino is in the default `make up` set; `cli` depends on kafka and trino healthy and mounts `/runs` | The image's `jvm.config` sizes the heap at `MaxRAMPercentage=80`, about 1.2 GB of the 1536m limit, which leaves too little room for code cache and metaspace, and an explicit `-Xmx` wins over the percentage; the image's 10 s start period is short for a JVM on a laptop; `check` reads the manifests from `/runs` and needs both Kafka (DLQ) and Trino |
